1. **The plan fails because blind proposals are built before anyone can tell whether they changed anything.** The roadmap calls blind proposals "highest immediate user value", yet the engine facts say the Evaluator's scores are read by nothing and the decisions ledger had never been rendered before 2026-10-05. Anti-sycophancy detection, which is the only thing that would measure blind versus revealed drift, is step 6 and "measurement only". Three months in, the developer has a blind mode and no way to show it beats the old one, so it gets abandoned or left as an unvalidated default. The failure mode is shipping a behaviour change with its instrument last.

2. **"Blind proposals work without phases" is half true, and the other half costs rework.** The engine already runs fixed propose -> critique -> evaluate rounds from a mode, but between rounds agents see only the 3-sentence Position Summary blocks, not full text. Suppressing prior context in "propose" therefore collides with the ledger, the open questions carried forward and the prior design-doc headings. These are all context sections the budget enforcer trims. The roadmap does not say which of them a blind proposer may see. Whichever way it is decided at 3 AM, the first multi-question session leaks the previous question's conclusions into a supposedly blind round, and the result is quietly contaminated.

3. **The estimates assume a phase system that is not a 2-3 day job.** The open questions in the roadmap say it plainly: nobody has decided how transitions trigger (time, convergence or round count), and Gap 3 in implementation-gaps.md is labelled "Large -- full design + implementation". Meanwhile key takeaways (1 day) and stale detection (2 days) both depend on phase boundaries, and the voting prompt (Gap 1) is unwritten. Phase work will absorb weeks, and steps 4 to 6 stall behind it. The plan looks sequential but is really one unscoped dependency with three downstream items waiting on it.

4. **Key takeaways and stale detection duplicate machinery that already exists in weaker form.** The ledger already carries DECIDED, CONTESTED and OPEN lines forward, and its synthesis template was only rendered for the first time today. Adding a voting side-channel (5 extra `claude -p` calls per proposal) before observing what the ledger produces in real sessions is premature. The 17 sessions on disk predate the ledger, so there is no evidence of stale or repetitive output to detect.

5. **The BIT "parallel track" is a fiction for a solo developer.** There is one person, and "parallel" just means the critical path slips whenever BIT is more fun. Nothing in the roadmap ties BIT to any engine fact, so it is the likeliest item to consume the time.
