# How does the Morning Brief get generated?

*Generated: 2026-03-18 03:49 | Question 1 | 105s | Mode: compete*

## Decisions

### Generation Timing: All-at-Once at Session End

The Morning Brief is generated by a single CLI call after all questions have been processed. No incremental fragment accumulation, no partial briefs mid-session. One call, one artifact, one failure surface.

Rationale: At V1 scale (up to 10 questions per session), the extracted decisions and open questions total roughly 3-5K tokens. There is no context overflow problem to solve. Fragment accumulation adds per-round failure points, prompt maintenance burden, and the risk of contradictory fragments misleading users when read without synthesis.

### Input Assembly: Structured Extractions Only

The brief prompt receives concatenated `decisions.json` and `open_questions.json` files from each round. It does not receive full design docs, transcripts, or raw agent outputs.

Rules:
- Each round's extraction must produce a `decisions.json` and `open_questions.json` before the brief can be generated.
- If a round's extraction failed or is missing, the brief call proceeds without it. The verification pass (below) will catch the gap.
- Design docs are reference material for human deep-dives. They are never brief input.

### Risk Flags: Derived During Extraction, Not at Synthesis Time

Risk flags are unresolved critiques -- decisions where the critic round raised concerns that were acknowledged but not resolved in the evaluation step.

Rules:
- The evaluator synthesis prompt must tag each decision with a resolution status: `resolved`, `partially_resolved`, or `unresolved`.
- The evaluator synthesis prompt must output a confidence tag per decision (e.g., `high`, `medium`, `low`) based on the degree of consensus reached during the evaluate round.
- The brief prompt filters on these tags. It does not infer confidence or identify risks independently.
- No numerical confidence thresholds (e.g., "below 80%") appear in the brief prompt. Confidence categories come from upstream extraction, grounded in actual session data.

### Brief Prompt

```
You are summarizing an overnight autonomous design session for a human
who has 5 minutes. They need to know what was decided, what is shaky,
and what needs their input before work proceeds.

INPUT: Extracted decisions and open questions from each discussion round,
with confidence tags and critique resolution status.

OUTPUT: Morning Brief in exactly this format:

## Decisions Made
Numbered list. One line each. Append confidence tag if medium or low.

## Risk Flags
Decisions where critic concerns were acknowledged but not fully resolved.
State the concern, not just the decision.

## Open Questions Requiring Human Input
Unresolved items that block downstream work or require judgment calls
outside the scope of the discussion.

## Recommended Reading Order
Which design docs to read first if the reader wants to go deeper.
Order by importance to near-term decisions, not by session order.

No prose paragraphs. No executive summary. Every line must be scannable.
```

### Output Verification

After the brief is generated, run a verification pass before writing the final artifact.

Rules:
- Count the number of decisions present in the input files.
- Count the number of decisions listed in the generated brief.
- If the output count diverges from the input count by more than 20%, append this notice to the top of the brief: `NOTE: This summary may be incomplete. Review decisions files directly in the session folder.`
- This check catches the primary failure mode: the LLM call succeeds but silently drops decisions or invents content.
- The verification is a count comparison, not a semantic review. It is cheap and deterministic.

### Fallback on Call Failure

If the brief generation call fails (timeout, API error, malformed output), concatenate the raw `decisions.json` files into a flat markdown list and write that as the Morning Brief.

Rules:
- The fallback brief uses this header: `## Morning Brief (auto-generated from raw decisions -- synthesis call failed)`
- Each round's decisions are listed under a subheading with the question that produced them.
- No retry logic. The orchestrator is a batch job. Graceful degradation beats retry complexity.
- The fallback is ugly but complete. The user gets every decision, unfiltered.

### Context Overflow: Not Addressed in V1

At 10 rounds, extracted decisions and open questions fit comfortably in context. No truncation policy, no split-and-merge strategy, no front-loading or back-loading heuristics.

If a future version scales beyond what fits in a single context window, the approach is: split rounds into groups, summarize each group, merge summaries. Do not build this now.

### Format Principles

- Four sections, always in the same order: Decisions, Risk Flags, Open Questions, Reading Order.
- No section is ever omitted. If there are no risk flags, the section reads "None identified."
- Every decision line is self-contained. A reader should not need to cross-reference another line to understand it.
- The brief targets 90-second scannability. If a section exceeds 15 lines, the extraction upstream is too granular, not the brief's problem.
