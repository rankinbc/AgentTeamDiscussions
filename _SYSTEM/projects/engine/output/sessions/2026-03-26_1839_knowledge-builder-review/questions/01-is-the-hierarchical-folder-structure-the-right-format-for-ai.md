# Is the hierarchical folder structure the right format for AI consumption?

*Generated: 2026-03-26 18:43 | Q1 | 203s | Mode: compete*

## Decisions

1. **The hierarchical folder structure remains canonical storage.** No migration to database, single document, or graph. The hierarchy's pre-sliced granularity (atomic files with known token costs) is its primary advantage for AI consumption. Alternatives fail characteristically: databases lose prose context, monolithic documents are context bombs, graphs require traversal tooling absent from most agentic pipelines.

2. **Storage format and consumption format are separate concerns.** The hierarchy solves organization. A lightweight manifest solves selection. These are not competing solutions — they are different layers of the same pipeline.

3. **A token-counted file manifest is the required addition.** This manifest is a structured index keyed by system and task-type, with token estimates attached to each file path. It is not a semantic synthesis; it is a literal, enumerable map. An agent building clone code for combat loads the manifest first, reads the relevant cluster, knows its token budget before fetching anything.

4. **The semantic index proposal is rejected.** A derived artifact with an undefined regeneration trigger is worse than no artifact — stale indexes produce confident wrong navigation. The manifest does not require LLM synthesis; it is generated mechanically from the file tree with token counts appended.

5. **The cross-reference extension is rejected as the primary solution.** Prose cross-references in READMEs are human navigation aids, not machine-traversable links. They have no enforced validity, no dead-link detection, and degrade silently when structure changes. They may coexist as human-facing documentation but do not solve agent file selection.

6. **Context budget is the first-order constraint, not navigation complexity.** Silent truncation — an agent loading what fits rather than what's needed — produces confidently wrong output with no error signal. All structural decisions are downstream of this constraint. The manifest directly addresses it by making token cost visible before loading.

7. **Before any further structural iteration, one instrumented agent task must be executed.** The test is: ask an agent to produce a requirements doc or write clone code for the combat system. Instrumentation must capture: which files were requested, which were loaded, total token consumption, and where output diverges from source material. Output quality alone is insufficient signal — selection recall is the metric.

## Rules

### Manifest Format

- One manifest per game, located at `game_specs/MANIFEST.json` (or `.yaml`).
- Each entry contains: file path (relative to `game_specs/`), system tag, task-type tags, token estimate, and provenance tier of the highest-confidence claim in the file.
- Task-type tags are drawn from a controlled vocabulary: `clone-code`, `requirements`, `balance-reference`, `narrative`, `cross-system`.
- Token estimates are computed at index time, not inferred. Any regeneration of the manifest recomputes estimates from the actual files.

### Manifest Lifecycle

- The manifest is regenerated by the organizer agent role after any research wave completes and files are slotted into the hierarchy.
- Regeneration is triggered by the same event that closes a research wave: human approval between waves already exists as a gate; manifest regeneration is added to that gate as a required step before the next wave begins.
- The manifest is a versioned artifact. Each regeneration appends a timestamp. Agents read the latest version; prior versions are retained for diff and audit.

### Hierarchy Rules (unchanged)

- Depth = precision. Top-level READMEs carry prose overviews; leaves carry exact formulas, tables, and pseudocode.
- Flexible depth per system. No minimum or maximum depth is enforced.
- Every factual claim retains provenance tagging: `ROM_VERIFIED > COMMUNITY_VERIFIED > GUIDE_SOURCED > INFERRED > OBSERVED`.
- `[UNKNOWN: est X-Y]` tags remain for unfindable data.

### Agent Consumption Pattern

- Developer agents load the manifest first. The manifest is always the entry point for any task against a game's knowledge base.
- The agent selects a file cluster from the manifest by matching system and task-type tags against the task description.
- Token budget is checked before fetching. If the selected cluster exceeds available context, the agent requests only the highest-provenance files first and surfaces the gap explicitly — it does not silently truncate.
- Cross-system dependencies appear in the manifest as explicit file path references under a `dependencies` key on the entry that owns the dependency. These are machine-readable paths, not prose descriptions.

### Cross-References

- READMEs may contain a `## Cross-References` section for human readers.
- These sections are not the mechanism for agent file selection. The manifest is.
- Cross-reference prose is not validated for correctness. The manifest's dependency entries are the authoritative machine links.

### Test Protocol

- Before any structural change to the hierarchy or manifest schema is made, the instrumented task must be run on the current state of `analysis_games/MagicOfScheherazade/`.
- The combat system is the first target: task is "produce a requirements doc for the action combat system."
- Instrumentation captures: files requested, files loaded, token totals, and output accuracy against `damage_formulas.md` and `enemy_stats.json` ground truth.
- Results from this test determine whether the manifest schema requires revision before Level 2 research waves begin.
